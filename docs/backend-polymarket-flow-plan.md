# План изменений backend для флоу "Инсайдер Маркет"

Документ фиксирует backend-изменения для новой публичной навигации и сценариев, похожих на Polymarket.

## Цели

- Переименовать продукт в публичных конфигурациях и документации на "Инсайдер Маркет".
- Сделать публичную витрину вокруг событий, лидерборда и последних новостей.
- Поддержать главный экран с выделенным событием, вероятностями исходов и списком событий.
- Дать зарегистрированным пользователям покупку исхода события, чат события, отправку новости и предложение события из слуха.
- Сохранить текущую сервисную архитектуру и границы слоев.

## Базовые правила доступа

- Публичные `GET`:
  - список событий и детали события;
  - главный экран;
  - список лидеров;
  - последние публичные слухи и детали слуха;
  - публичный профиль пользователя, если включена опция публичности.
- Авторизованные действия:
  - покупка исхода через `market_service`;
  - отправка новости по событию;
  - чат события;
  - предложение события из слуха;
  - изменение своего профиля и публичности.
- Модераторские действия остаются за текущими permissions.

## P0. Публичная витрина событий

### 1. Категории и фильтры событий

- Добавить нормализованную категорию события: `transfers`, `matches`, `dismissals`, `titles`, `other`.
- Не хранить категории только в `candidate_payload`; вынести в явное поле доменной сущности `Event`, DTO, схемы API, table и mapper.
- Добавить фильтр `category` в `GET /api/v1/events`.
- Для совместимости оставить `candidate_payload` как техническое расширение.

Критерий готовности:

- Клиент может получить события по разделам "Трансферы", "Игры", "Отставки и названия", "Другое".

### 2. Сортировки списка событий

- Добавить `sort` в `GET /api/v1/events`:
  - `created_at`;
  - `deadline_at`;
  - `popularity`.
- Для популярности использовать агрегат из market-активности: количество ставок и/или объем ставок.
- Сортировка должна быть реализована на уровне репозитория через table-column expressions.

Критерий готовности:

- Экран "События" может переключать сортировку без клиентской постобработки.

### 3. Карточки событий с market-сводкой

- Добавить read-модель для публичной карточки события:
  - `event_id`;
  - название;
  - описание;
  - дата разрешения;
  - статус;
  - категория;
  - количество ставок;
  - вероятности исходов;
  - market id для покупки исхода.
- Реализовать через application-level aggregator/use case, который читает `event_service` и `market_service` без нарушения зависимостей.
- Если прямые межсервисные чтения уже идут через gateway/BFF, разместить aggregator в gateway/BFF-слое; не импортировать репозитории одного сервиса в другой.

Критерий готовности:

- Главный экран и экран событий получают готовые карточки одним контрактом или небольшим числом публичных контрактов.

### 4. Главное событие

- Добавить endpoint витрины, например `GET /api/v1/feed/home` или gateway route:
  - главное событие;
  - список событий ниже;
  - доступные фильтры навигации.
- Правило выбора главного события зафиксировать в use case:
  - активное событие с открытым market;
  - максимальная популярность за период;
  - fallback на ближайшую дату разрешения.
- Вернуть probability dashboard fields: `yes_probability`, `no_probability`, `yes_pool`, `no_pool`, `bets_count`.

Критерий готовности:

- Главный экран не собирает данные из несвязанных ручек вручную.

## P1. Детали события

### 5. Связанный слух и источник

- Расширить детали события связью на `source_rumor_id`.
- В ответе деталей события вернуть:
  - исходный слух;
  - источник слуха;
  - текущий market;
  - список последних публичных новостей по событию.
- Для слуха использовать данные `rumor_service`; источник получать через `sources`.

Критерий готовности:

- Экран деталей события показывает исходный слух и источник без дополнительных неявных запросов.

### 6. RSS/новости по событию

- Определить сущность новости по событию:
  - либо расширить `rumor_service` связью `event_id`;
  - либо добавить отдельный `event_news` контур, если новости отличаются от слухов по жизненному циклу.
- Для первого этапа предпочтительно расширить `rumor_service`: добавить `event_id`, `is_public`, `published_at`.
- Добавить `GET /api/v1/events/{event_id}/news` или агрегированный блок в деталях события.
- Отправка новости зарегистрированным пользователем:
  - `POST /api/v1/events/{event_id}/news`;
  - статус по умолчанию `new`/`pending`;
  - публичной становится после модерации.

Критерий готовности:

- Детали события показывают последние публичные новости, а пользователь может отправить новость на модерацию.

### 7. Чат события

- Добавить event-scoped chat:
  - `GET /api/v1/events/{event_id}/chat/messages`;
  - `POST /api/v1/events/{event_id}/chat/messages`;
  - websocket channel для новых сообщений.
- Хранить сообщения отдельно от уведомлений; `notification_service` можно использовать как транспорт, но не как источник истины.
- Проверять авторизацию на запись и чтение чата; публичное чтение можно открыть только если это явно подтверждено продуктом.
- Добавить rate limit на отправку сообщений.

Критерий готовности:

- Авторизованный пользователь видит чат события и отправляет сообщения с привязкой к своему `user_id`.

## P1. Торговый сценарий

### 8. Покупка исхода

- Использовать существующий `POST /api/v1/markets/{market_id}/bets`.
- Убрать `user_id` из публичной схемы `BetCreate` или сделать его игнорируемым в presentation layer: владелец уже берется из JWT.
- Проверить, что схема поддерживает покупку конкретного исхода через `side`.
- Для модального окна фронта добавить preview endpoint, если API должен показывать ожидаемые shares/price до покупки.

Критерий готовности:

- Зарегистрированный пользователь покупает исход из карточки или деталей события без передачи `user_id` с клиента.

## P1. Лидерборд и публичные профили

### 9. Публичный leaderboard

- Сделать `GET /api/v1/ratings/leaderboard` публичным.
- Добавить фильтр периода:
  - `week`;
  - `month`;
  - `all_time`.
- Если текущая модель хранит только накопленный профиль, добавить агрегаты/материализацию по периодам на основе rating events.
- Расширить read-модель leaderboard:
  - место;
  - nickname/display name;
  - рейтинг;
  - ROI;
  - точность;
  - total predictions;
  - achievements;
  - `is_profile_public`;
  - ссылка/признак доступности профиля.

Критерий готовности:

- Экран "Список лидеров" строится публично и умеет переключать период.

### 10. Публичность профиля

- Добавить в `profile_service` поле публичности профиля, например `is_public`.
- Расширить `ProfileUpdate`, `ProfileResponse`, domain entity, table, mapper и миграцию.
- Добавить публичный read endpoint для профиля, который:
  - возвращает данные только если `is_public = true`;
  - не раскрывает баланс и приватные операции;
  - может включать публичную статистику из `rating_service`.
- Текущий owner/admin read оставить для полного профиля.

Критерий готовности:

- Из лидерборда можно перейти только в публичный профиль, а приватный профиль не раскрывает данные.

## P1. Последние новости и предложение события

### 11. Публичные слухи

- Зафиксировать статус/флаг публичности слуха, который выставляет модератор.
- Добавить публичный endpoint `GET /api/v1/rumors/public` с полями:
  - `rumor_id`;
  - источник;
  - title/text;
  - tags;
  - created/published date.
- Детали слуха должны возвращать слух, источник и связанные события, если они уже созданы.

Критерий готовности:

- Экран "Последние новости" показывает только слухи, разрешенные модератором к публикации.

### 12. Предложить событие из слуха

- Добавить `POST /api/v1/rumors/{rumor_id}/event-proposals` для авторизованных пользователей.
- На backend это должно создавать неактивное событие в `event_service`:
  - `source_rumor_id = rumor_id`;
  - `status = draft` или `pending moderation`;
  - `created_by_user_id` из JWT;
  - `submit_for_moderation` по решению продукта.
- Не давать клиенту подменять `created_by_user_id`.

Критерий готовности:

- Пользователь может предложить событие из деталей слуха, а модератор видит его в очереди событий.

## P2. Профиль игрока

### 13. Статистика и личная информация

- Собрать профильный read endpoint для текущего пользователя:
  - личная информация из `profile_service`;
  - баланс и доступный баланс;
  - статистика игрока из `rating_service`;
  - achievements;
  - последние активности.
- Сохранить обновление личной информации через `PATCH /api/v1/profiles/{user_id}`.
- Добавить настройку публичности в ту же форму или отдельный endpoint.

Критерий готовности:

- Экран профиля показывает статистику и позволяет менять личные данные и публичность.

## P2. Gateway, настройки и бренд

### 14. Навигационный metadata endpoint

- Добавить lightweight endpoint для frontend, если меню не должно быть захардкожено:
  - brand: "Инсайдер Маркет";
  - top sections: events, leaderboard, latest news;
  - filter groups для выбранного раздела.
- Если меню статичное на frontend, backend endpoint не обязателен.

### 15. API gateway routes

- Проверить маршрутизацию gateway для новых публичных endpoints.
- Настроить public rate limit отдельно для главной витрины, событий, лидерборда и новостей.
- Убедиться, что mutating endpoints остаются за JWT и permissions.
